# ADR-001: Temporary stderr Lock

## Контекст

Модуль `dds_core/infrastructure/pymupdf_text_extractor.py` перехватывает
диагностический вывод PyMuPDF через временную подмену файлового
дескриптора 2 (`stderr`) на канал (`os.pipe`). Функция
`_capture_stderr` выполняет последовательность:

```
os.dup(2) → os.pipe() → os.dup2(write_fd, 2) → func(...) → os.dup2(saved_fd, 2) → os.read(read_fd)
```

PyMuPDF пишет ошибки (например, «syntax error: invalid key in dict»)
**напрямую в fd 2**, минуя `sys.stderr`. Без перехвата эти сообщения
попадали бы в лог uvicorn, а не в диагностику конкретного документа —
терялась бы связь между ошибкой и обрабатываемым файлом.

**Проблема.** fd 2 — **процессный** ресурс, не потоковый. В
презентационном слое два эндпоинта вызывают PyMuPDF-операции
**параллельно** в `scan_executor` (ThreadPoolExecutor, 6 воркеров):

- `POST /api/documents/{id}/pages/{n}/render` — PNG-рендер страницы
  (`PyMuPDFTextDocument.render_page`).
- `POST /api/documents/{id}/pages/{n}/highlights` — построение индекса
  слов (`PyMuPDFTextDocument.build_word_index`).

Оба вызывают `_capture_stderr`. При одновременной работе двух потоков
последовательности `dup → dup2 → func → dup2 → read` перекрываются:
поток A сохраняет fd 2 (уже подменённый потоком B), поток B
восстанавливает fd 2 (уже восстановленный потоком A). Результат —
перепутанный вывод, потерянные сообщения, редкие ложные срабатывания
диагностики.

**Воспроизводимость.** Гонка проявляется нерегулярно. Симптомы
наблюдались при нагрузочных прогонах: в логе `dds.log` сообщения
об ошибках одного документа иногда приписывались другому.
Условие воспроизведения: одновременная работа ≥ 2 запросов
`/render` или `/highlights` на одну и ту же вкладку при активном
индексировании в другом контексте.

**Контекст среды.** Функция `_capture_stderr` вызывается только из
инфраструктурного слоя. Application layer (ScanPipeline, TextIndexer)
выполняет PyMuPDF-операции в `ProcessPoolExecutor` (извлечение
текста) — там fd 2 у каждого процесса свой, конфликта нет. Гонка
возникает исключительно в `scan_executor` (потоки), используемом
веб-слоем.

## Альтернативы

### Альтернатива 1: Оставить как есть

**Описание.** Не вводить блокировку. Считать гонку редкой и
приемлемой.

**Плюсы.**
- Никаких изменений в коде.
- Параллелизм PyMuPDF-операций в `scan_executor` сохраняется на
  максимуме.

**Минусы.**
- Гонка реальна и воспроизводима при нагрузке.
- Потеря диагностики — критично для отладки сложных PDF
  (нестандартные CAD-экспорты, повреждённые страницы).
- Ложные сообщения об ошибках вводят операторов в заблуждение.

**Итог.** Отклонена. Надёжность диагностики важнее незначительной
потери параллелизма на редких конкурентных запросах.

### Альтернатива 2: `threading.Lock` вокруг `_capture_stderr` (временная мера)

**Описание.** Модульная блокировка `_stderr_lock: threading.Lock`,
оборачивающая всю последовательность `dup → dup2 → func → dup2 →
read` в `_capture_stderr`. Одновременно в процессе выполняется не
более одного вызова `_capture_stderr`.

**Плюсы.**
- Минимальные изменения: один импорт + одна константа + обёртка
  `with _stderr_lock:` вокруг тела функции.
- Полностью устраняет гонку: инвариант «не более одного выполнения
  одновременно» детерминирован.
- Прост в реализации и верификации: легко покрывается тестом на
  счётчике одновременных выполнений.
- Не влияет на извлечение текста через `ProcessPoolExecutor` —
  каждый процесс имеет собственный fd 2, блокировка процесса не
  конкурирует с другими процессами.

**Минусы.**
- Сериализует PyMuPDF-операции в `scan_executor`: одновременные
  `/render` и `/highlights` выполняются последовательно.
- Снижает throughput на нагрузочных сценариях (например,
  параллельный просмотр нескольких документов разными
  пользователями).
- Является **временной** мерой: фиксирует архитектурную
  неполноту (PyMuPDF в общих потоках), которая должна быть
  устранена в Фазе 4.

**Итог.** Принята как временная мера до Фазы 4.

### Альтернатива 3: Изоляция PyMuPDF в отдельные процессы (`ProcessTaskRunner`)

**Описание.** Вынести все PyMuPDF-операции (рендер, построение
индекса слов, извлечение текста) в `ProcessPoolExecutor` с
`ProcessTaskRunner`. Каждый процесс имеет собственный fd 2 —
гонка исчезает по построению. Блокировка не нужна.

**Плюсы.**
- Полное устранение класса проблем: fd 2 становится
  процессно-локальным.
- Устойчивость к сегфолтам PyMuPDF (не роняют основной процесс).
- Естественная изоляция состояния между запросами.
- Устраняет необходимость в `threading.Lock` и позволяет
  параллелить PyMuPDF-операции.

**Минусы.**
- Значительная инженерная работа: `ProcessTaskRunner` — отдельный
  модуль с forkserver, IPC, таймаутами, graceful shutdown.
- Оверхед fork+IPC на каждую операцию (десятки миллисекунд);
  для рендера одной страницы это может быть сопоставимо с самим
  рендером.
- Требует переработки `scan_executor` и `text_extractor` в
  `dds_web/api.py` — дополнительные риски.
- Запланирована отдельная фаза (Фаза 4 плана v9), не может быть
  выполнена как часть Фазы 1.

**Итог.** Отложена до Фазы 4 как целевое решение. В Фазе 1
нереализуема (превышает объём фазы, требует инфраструктуры
`ProcessTaskRunner`).

### Альтернатива 4: `contextlib.redirect_stderr`

**Описание.** Использовать `contextlib.redirect_stderr(io.StringIO())`
для перехвата stderr.

**Плюсы.**
- Идиоматично для Python.
- Не требует `dup`/`dup2` и, следовательно, не создаёт гонку
  за fd 2.
- Кроссплатформенно.

**Минусы.**
- **Не работает.** PyMuPDF пишет на уровне **файлового
  дескриптора 2** через нативный C-код, минуя
  `sys.stderr`. `redirect_stderr` подменяет только Python-объект
  `sys.stderr`; нативный вывод в fd 2 остаётся неотслеженным.
- Это документированное поведение PyMuPDF и его корневой
  зависимости (MuPDF).

**Итог.** Отклонена как технически нерабочая.

### Альтернатива 5: `os.pipe` на каждый вызов без блокировки

**Описание.** Избежать подмены глобального fd 2, читая вывод
через отдельный канал, ассоциированный только с текущим потоком.

**Плюсы.**
- Теоретически устраняет гонку без сериализации.

**Минусы.**
- **Нереализуемо** без модификации PyMuPDF. PyMuPDF всегда пишет
  в fd 2 — это зашито в нативный код. Перенаправить его вывод
  в per-thread канал невозможно без пересборки библиотеки.
- Единственный способ «поймать» вывод — подменить глобальный fd 2,
  что и создаёт гонку.

**Итог.** Отклонена как нереализуемая.

### Альтернатива 6: Отключить перехват stderr

**Описание.** Не перехватывать диагностику PyMuPDF, позволить
ей идти в общий stderr процесса.

**Плюсы.**
- Устраняет гонку (нет `dup2`).
- Упрощает код.

**Минусы.**
- Теряется связь между ошибкой и обрабатываемым документом:
  диагностика попадает в общий поток stderr uvicorn.
- Невозможно корректно пометить конкретный файл как ошибочный
  (`FileProcessingFailed`) на основе сообщений PyMuPDF.
- Регресс по сравнению с текущим поведением.

**Итог.** Отклонена. Потеря диагностики — критична для
production-эксплуатации.

## Решение

Применяется **Альтернатива 2**: модульная блокировка
`threading.Lock` вокруг критической секции `_capture_stderr`.

### Ключевые детали реализации

- **Модульная константа.** `_stderr_lock: threading.Lock` на уровне
  модуля `pymupdf_text_extractor.py`. Не `RLock`: вложенности
  вызовов `_capture_stderr` нет и не предполагается.
- **Обёртка.** Тело функции `_capture_stderr` целиком помещено в
  `with _stderr_lock:`. Логика внутри (последовательность `dup →
  dup2 → func → dup2 → read → close`) не изменена.
- **Область действия.** Блокировка действует в пределах процесса.
  Для `ProcessPoolExecutor` (извлечение текста в `ScanPipeline`)
  она не нужна — каждый процесс имеет собственный fd 2. Для
  `scan_executor` (потоки) она сериализует PyMuPDF-операции
  веб-слоя.
- **Тестовое покрытие.** `tests/test_pymupdf_stderr_lock.py`
  проверяет инвариант через thread-safe счётчик одновременных
  выполнений: 4 потока × 50 итераций, `max_observed == 1`.

### Инварианты

- **Одновременное выполнение `_capture_stderr` в процессе — не
  более одного.** Достигается за счёт модульной блокировки.
- **Результат `_capture_stderr` соответствует вызванной функции.**
  Логика перехвата не изменена, контракт возврата
  `(result, captured_output)` сохранён.
- **Извлечение текста через `ProcessPoolExecutor` не затронуто.**
  Каждый процесс имеет собственный fd 2 и собственную копию
  `_stderr_lock`; между процессами конкуренции нет.

## Последствия

### Положительные

- Гонка за fd 2 устранена детерминированно. Диагностика PyMuPDF
  надёжно связывается с обрабатываемым документом.
- Ложные сообщения об ошибках в логе исчезают.
- Изменение локализовано: один импорт, одна константа, одна
  строка обёртки. Риск регресса минимален.
- Извлечение текста (основная нагрузка по CPU) не затронуто —
  выполняется в процессах, где блокировка не конкурирует.

### Отрицательные

- **Снижение throughput `scan_executor`.** Одновременные
  `/render` и `/highlights` на одном процессе выполняются
  последовательно. На нагрузочных сценариях (много активных
  пользователей) время ответа эндпоинтов предпросмотра растёт
  пропорционально количеству конкурентных запросов.
- **Блокировка не предотвращает деградацию при сегфолте
  PyMuPDF.** Если PyMuPDF падает с SIGSEGV, весь процесс
  uvicorn завершается. Изоляция через процессы (Альтернатива 3)
  решила бы эту проблему, но не входит в Фазу 1.

### Нейтральные

- API `_capture_stderr` не изменился; внешние потребители не
  затронуты.
- Тесты сериализации добавляют ~250 мс к общему времени прогона.
- Документация модуля и ADR фиксируют временный характер меры.

### Известные ограничения

- **Мера временная.** Устраняется в Фазе 4 с появлением
  `ProcessTaskRunner` (см. ADR-004). После Фазы 4 запись
  получит статус `superseded`, `Superseded-by: ADR-004`.
- **Сериализация PyMuPDF в потоках.** Осознанное принятие
  компромисса: снижение throughput в пользу корректности
  диагностики. При росте нагрузки до уровня, где throughput
  критичен, приоритет Фазы 4 повышается.
- **Не решает проблему сегфолтов PyMuPDF.** Это задача
  Альтернативы 3 (process-изоляция). В рамках Фазы 1 сегфолт
  остаётся фатальным для процесса uvicorn.
