# Architecture Decision Records (ADR) журнал DDS

Журнал архитектурных решений Deep Doc Search. Каждая запись (ADR)
фиксирует одно значимое решение: контекст, альтернативы, выбранный
вариант и последствия. Цель — сохранить для будущих разработчиков
ответ на вопрос «почему здесь так сделано?» без археологии по
commit-истории и чатам.

---

## 1. Зачем это в DDS

Проект прошёл через серию рефакторингов (v5 → v9), в ходе которых
принимались неочевидные решения:

- `ProcessTaskRunner` использует `process-per-task`, а не
  `multiprocessing.Pool`;
- `normalize_text` живёт в `domain`, хотя формально это утилита;
- `subprocess_tasks` импортирует `infrastructure`, что запрещено
  для остальных слоёв;
- `Queue.put` обёрнут в `_safe_put` с явным `pickle.dumps`;
- `forkserver` вместо `fork` на Linux;
- `?v={{ build_hash }}` через `env.globals`, а не `app.state`;
- `AbortController` вместо счётчика `_seq` для клиентской защиты
  от race condition;
- разделение read-контракта на `IDocumentRepository` (ADR-008),
  а не расширение `IIndexWriter` до write+read.

Без журнала такие решения выглядят как произвольные. С журналом —
как результат анализа альтернатив. Любая попытка «упростить» их
наталкивается на ADR, где объяснено, почему более простой вариант
не работает.

Дополнительно ADR-журнал используется инструментами CI:

- `check_import_linter_exceptions.py` читает `exceptions.yaml`
  (см. раздел 6), который ссылается на ADR с обоснованиями;
- `check_deprecations.py` — аналогично для `DEPRECATIONS.yaml`;
- ревьюер в PR проверяет, что изменение архитектуры сопровождается
  ADR.

## 2. Формат записи

Используется формат Michael Nygard (2011), адаптированный под DDS.
Каждый ADR содержит секции:

| Секция | Обязательна | Описание |
|---|---|---|
| Заголовок | да | `# ADR-NNN: <Краткое название>` |
| Метаданные | да | Дата, автор, статус, supersedes/superseded-by |
| Контекст | да | Какую проблему решаем, что не работает сейчас |
| Альтернативы | да | Рассмотренные варианты с обоснованием отказа |
| Решение | да | Что выбрали и почему именно это |
| Последствия | да | Плюсы, минусы, известные ограничения |
| Ссылки | опционально | Связанные ADR, внешние материалы, issue |

Шаблон — `ADR-000-template.md`. Копируется при создании нового ADR.

---

## 3. Именование файлов

```
ADR-NNN-<kebab-case-name>.md
```

Правила:

- `NNN` — трёхзначный номер, начиная с `001`. **Не переиспользуется.**
  При отклонении ADR номер остаётся занятым со статусом `rejected`.
- `<kebab-case-name>` — краткое название на английском, 2–5 слов.
  Английский — для совместимости с grep/URL; русский может
  использоваться в заголовке внутри файла.

Примеры:

- `ADR-001-temporary-stderr-lock.md`
- `ADR-004-process-task-runner.md`
- `ADR-005-document-index-plan.md`
- `ADR-007-client-abort-controller.md`
- `ADR-008-read-side-sql-cleanup.md`

Особый случай: `ADR-000-template.md` — шаблон, не является записью.

## 4. Статусы и жизненный цикл

Каждый ADR имеет один из статусов:

| Статус | Значение |
|---|---|
| `proposed` | Предложен, обсуждается. Не обязателен к исполнению. |
| `accepted` | Принят. Обязателен к исполнению. Реализация в коде. |
| `rejected` | Рассмотрен и отклонён. Фиксируется, чтобы не предлагать повторно. |
| `deprecated` | Ранее принят, но устарел. Замены пока нет. |
| `superseded` | Заменён другим ADR. Обязательно поле `superseded-by`. |

**Правила переходов:**

- `proposed` → `accepted` — после ревью и согласования с
  ответственными.
- `proposed` → `rejected` — если альтернатива выбрана другая.
- `accepted` → `deprecated` — если решение перестало применяться,
  но формальной замены нет.
- `accepted` → `superseded` — если принят новый ADR,
  перекрывающий этот. **Файл старого ADR не удаляется**; в шапке
  добавляется `superseded-by: ADR-NNN`, в новом — `supersedes: ADR-XXX`.

**Пример из DDS:** ADR-001 (`temporary-stderr-lock`) имел статус
`accepted` до Фазы 4, затем стал `superseded` после принятия ADR-004
(`process-task-runner`), потому что временный `threading.Lock` был
заменён изоляцией PyMuPDF в отдельные процессы.

## 5. Шапка ADR

В каждом ADR первые строки после заголовка — метаданные в виде
таблицы (для читаемости) либо блока `key: value` (для парсинга):

```markdown
# ADR-004: ProcessTaskRunner

| Поле | Значение |
|---|---|
| Дата | 2025-01-15 |
| Автор | <имя> |
| Статус | accepted |
| Supersedes | ADR-001 |
| Superseded-by | — |
| Связанные ADR | ADR-005 |
```

Поля `Supersedes` и `Superseded-by` заполняются **только** когда
применимо; прочерк `—` используется для явного указания
«не применимо». Автоматический парсинг шапки не предусмотрен —
инструменты CI работают с `exceptions.yaml`, а не с ADR напрямую.

## 6. Связь с `exceptions.yaml`

`docs/architecture-decisions/exceptions.yaml` — источник истины
для архитектурных контрактов `import-linter`. Каждое **временное**
исключение (ослабление контракта) должно ссылаться на ADR в поле
`rationale`:

```yaml
contracts:
  - name: subprocess-tasks-isolation
    ...
    ignore_imports:
      - "dds_web.lifespan -> dds_core.subprocess_tasks.pdf_workers"

exception_lifecycle:
  - contract: subprocess-tasks-isolation
    import: "dds_web.lifespan -> dds_core.subprocess_tasks.pdf_workers"
    permanent: true
    rationale: >
      Composition root: единственная точка доступа к subprocess-worker'ам.
      Обоснование и альтернативы — в ADR-004.
```

**Правила:**

- Для `permanent: true` записей — обязательна ссылка на ADR в
  `rationale`. Это гарантирует, что «навсегда» подкреплено анализом.
- Для временных (`phase_removed_by: N`) — ссылка опциональна, но
  рекомендуется.
- `check_import_linter_exceptions.py` проверяет lifecycle, но не
  валидирует содержимое `rationale` — это задача ревью.

Аналогично устроена связь с `DEPRECATIONS.yaml`: каждая
deprecation-запись может ссылаться на ADR, вводящий удаление.

## 7. Создание нового ADR

Пошаговая инструкция:

1. **Определите необходимость.** ADR нужен, если решение:
   - отклоняется от общего архитектурного правила (компромисс);
   - имеет неочевидные альтернативы (выбор не «единственно
     возможный»);
   - фиксирует ограничение, которое будущий разработчик может
     попытаться снять.

   Если изменение тривиально и не вызывает вопросов — ADR не нужен.

2. **Найдите следующий номер.**
   ```bash
   ls docs/architecture-decisions/ADR-*.md | sort | tail -1
   ```
   Номер = максимальный + 1. Номера не переиспользуются даже для
   отклонённых ADR.

3. **Скопируйте шаблон.**
   ```bash
   cp docs/architecture-decisions/ADR-000-template.md \
      docs/architecture-decisions/ADR-NNN-<short-name>.md
   ```

4. **Заполните секции.** Не пропускайте «Альтернативы» — это самая
   ценная часть ADR. «Мы выбрали X» без обоснования, почему не Y и
   Z, — бесполезно для будущего читателя.

5. **Проставьте статус `proposed`.** Обсудите в PR.

6. **При согласовании** — статус `accepted`, ADR мержится вместе
   с кодом, реализующим решение.

7. **Ссылки.** Добавьте ADR в раздел 8 (индекс) этого README.

---

## 8. Superseding существующего ADR

Если решение отменяется:

1. Создайте новый ADR с собственным номером.
2. В новом ADR укажите `Supersedes: ADR-XXX`.
3. В старом ADR измените статус на `superseded` и добавьте
   `Superseded-by: ADR-YYY`.
4. **Не удаляйте старый ADR.** История важна: будущий разработчик
   может увидеть, почему решение приняли, а потом отменили —
   и избежать повторения ошибки.
5. Обновите ссылки в этом README.

## 10. Правила ревью

Reviewer проверяет ADR в PR по чек-листу:

- [ ] Номер уникален и не переиспользован.
- [ ] Имя файла соответствует конвенции `ADR-NNN-kebab-name.md`.
- [ ] Заголовок, метаданные, статус заполнены.
- [ ] Секция «Контекст» описывает **проблему**, а не решение.
- [ ] Секция «Альтернативы» содержит **минимум два** варианта
      (включая «ничего не делать», если применимо).
- [ ] Секция «Решение» объясняет, **почему** выбран этот вариант,
      а не только **что** выбрано.
- [ ] Секция «Последствия» честно перечисляет минусы и ограничения.
- [ ] Ссылки на связанные ADR корректны в обе стороны
      (supersedes / superseded-by).
- [ ] Индекс в разделе 8 обновлён.
- [ ] Если ADR вводит исключение в `exceptions.yaml` — запись
      добавлена с `rationale`, ссылающимся на ADR.

ADR без секции «Альтернативы» или с одной альтернативой
возвращается на доработку. Исключение — критичные исправления
безопасности, где времени на анализ мало (фиксируется в
«Контексте»).

## 11. Что не является ADR

- **Руководства** (`docs/user_guide.md`, `docs/deployment.md`) —
  описывают «как использовать», не «почему так».
- **Changelog** (`CHANGELOG.md`) — перечисляет изменения, не
  обосновывает.
- **Docstrings в модулях** — описывают контракт функции, не
  архитектурное решение.
- **Commit messages** — краткая справка, не развёрнутый анализ.
- **Исключения import-linter** — это факты в `exceptions.yaml`, а
  ADR обосновывает, почему они допустимы.

ADR не заменяет их; он **дополняет** их ответом на вопрос
«почему».

## 12. Внешние ссылки

- Michael Nygard, «Documenting Architecture Decisions» (2011) —
  оригинальное описание формата.
  <https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions>
- adr.github.io — каталог инструментов и примеров ADR.
  <https://adr.github.io/>
- Architecture Decision Record (Wikipedia) — обзор практики.
  <https://en.wikipedia.org/wiki/Architecture_decision_record>

Формат DDS следует Nygard с двумя отличиями:

1. **Обязательная секция «Альтернативы».** У Nygard она опциональна;
   в DDS без неё ADR не принимается. Причина: без анализа
   альтернатив ADR превращается в «мы так сделали», что бесполезно
   для будущего читателя.
2. **Явная связь с `exceptions.yaml`.** У Nygard нет такого
   механизма; в DDS он встроен для связи архитектурных решений
   с автоматическими проверками CI.
